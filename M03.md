1. OBJECTIVE

Establish a secure, production-minded authentication foundation for the Nutri AI modular monolith.

M03 must provide the minimum secure foundation required for users to:

Register an account.

Log in.

Obtain an authenticated session.

Access protected backend resources.

Refresh an expired/expiring access token through the refresh-token mechanism.

Log out and invalidate the refresh session.

Receive appropriate authentication/authorization errors.

Use the authentication flow from the React frontend.

The implementation must use the application's backend as the authoritative security boundary.

The frontend must never be treated as the final authorization layer.

2. PROJECT PRINCIPLES THAT APPLY

Follow these principles from PROJECT_SPEC.md:

Security is a first-class requirement.

Authentication and authorization belong to the backend.

Never store plaintext passwords.

Never log passwords, access tokens, refresh tokens, API keys, or sensitive health data.

Use DTOs rather than exposing JPA entities.

Validate external input.

Use least privilege.

Do not expose private user information across accounts.

Use environment-based secrets.

Use Flyway for every schema change.

Do not make the LLM authoritative for security decisions.

Keep the modular-monolith architecture.

Keep controllers thin and business logic in services/domain components.

Do not silently change approved technology versions.

The project specification explicitly requires registration, login, logout, access tokens, refresh tokens, token expiry, refresh-token invalidation/rotation where practical, password reset, account verification where practical, login throttling/rate limiting, and suspicious-login protection. It also explicitly prohibits plaintext passwords and logging credentials/tokens.

15. REFRESH TOKEN ARCHITECTURE

The project requires a refresh-token mechanism.

Select the browser token-storage architecture deliberately.

Recommended architecture for this project:

short-lived access token

access token held in frontend memory rather than persistent browser storage

refresh token delivered through a Secure, HttpOnly cookie

appropriate SameSite policy

refresh token persisted server-side in a revocable representation

refresh-token rotation where practical

logout revokes the refresh session

The refresh token must NOT be stored in:

localStorage

sessionStorage

frontend source code

logs

Do not expose the raw refresh token unnecessarily through JSON.

If the chosen architecture differs from the recommendation, document the security reasoning before implementation.
